# fruit_classification

266-way fruit image classification on **Fruits-360** (100×100), built as a
reproducible, Git+DVC versioned ML project.

```
git clone https://github.com/hassanimtiaz158/Deadpool-ml-collab.git
cd Deadpool-ml-collab
pip install -e ".[dev,pipeline]"     # or: make requirements
dvc pull                             # dataset (847 MB, from the DagsHub remote)
dvc repro                            # prepare -> train -> evaluate
cat reports/metrics.json
```

> The raw archive is **never** committed to Git — only its `.dvc` pointer is.
> `dvc push` always runs before `git push`.

---

## What this project does

| | |
| --- | --- |
| **Task** | Single-label image classification, 266 fruit classes |
| **Dataset** | [Fruits-360](https://www.kaggle.com/datasets/moltean/fruits), pre-resized to 100×100 (Kaggle / Moltean) |
| **Archive** | 188,984 JPEGs — 141,760 `Training`, 47,224 `Test` |
| **Features** | 272-d: 144-d HOG (4×4 cells × 9 orientation bins on a 32×32 grayscale plane) + 128-d HSV histogram |
| **Model** | Selected by measurement — see [`notebooks/02-model-selection.py`](notebooks/02-model-selection.py) |
| **Seed** | 42, declared in `params.yaml` |

## Why the data is *not* a CSV

Fruits-360 ships as images, so this project treats the dataset as an image
corpus and reads it **straight out of the DVC-tracked ZIP**. Decoding 189k
JPEGs is the single most expensive step (~14 min on 4 cores), so the `prepare`
stage caches features to `data/interim/` and every experiment after that reuses
the cache. See the performance table in [`REPORT.md`](REPORT.md).

## Common commands

| Command | Does |
| --- | --- |
| `make requirements` | install the pinned env plus dev/pipeline extras |
| `make lint` / `make format` | `ruff check` + `ruff format --check` |
| `make test` | run the unit tests |
| `make prepare` | build/refresh the feature cache (~14 min cold) |
| `make repro` | `dvc repro` (the whole pipeline) |
| `make compare` | train every candidate and write the leaderboard |
| `make smoke` | fast end-to-end run on the CI sample |
| `make experiments` | `dvc exp run` sweeps + `dvc exp show` |
| `make verify` | re-run the pipeline and print the test metrics |
| `make data-pull` | `dvc pull` |
| `make data-push` | `dvc push` **then** `git push`, in that order |

`dvc push` talks to DagsHub and needs a token — export `DAGSHUB_TOKEN` or put it
in the remote URL. `dvc push` must complete **before** `git push`, otherwise the
remote ends up holding pointers to objects nobody can pull.

## Pipeline stages

`dvc.yaml` defines three stages. Each depends only on the code, params and data
it actually reads, so `dvc repro` re-runs the minimum necessary.

| Stage | Reads | Writes |
| --- | --- | --- |
| `prepare` | `params.yaml`, the `.dvc`-tracked ZIP, `features.py`, `dataset.py` | `data/interim/full_features.npz`, `full_index.csv`, `full_manifest.json` |
| `train` | cached features, `models.py`, `train.py` | `models/model.joblib` |
| `evaluate` | trained model, cached features | `reports/metrics.json`, `reports/per_class_metrics.csv`, confusion matrix |

> **The feature cache is an intermediate, not a deliverable.** It is declared with
> `persist: false`, so it is never pushed to the DagsHub remote — it is fully
> derived from the raw archive plus `features.py`, and versioning it would add
> ~180 MB to every push for no benefit.
>
> The trade-off: DVC deletes a stage's outputs *before* re-running that stage, so
> changing anything in `prepare`'s `deps` (including editing `dvc.yaml` itself)
> forces a full **~14 minute** re-extraction of all 188,984 images. Run
> `dvc status` before committing a `deps` change.

### Artefact namespacing

Output paths are derived from `cache_tag`, so the CI smoke run can never
overwrite the real results:

| `cache_tag` | Model | Reports |
| --- | --- | --- |
| `full` (default) | `models/model.joblib` | `reports/metrics.json`, `reports/figures/` |
| `smoke` | `models/smoke_model.joblib` | `reports/smoke/metrics.json`, `reports/figures/smoke/` |

`evaluate` loads `models/model.joblib` instead of refitting, so `dvc repro` fits
each model once, not twice.

## Reproducibility guarantees

* **Every** hyperparameter, split ratio and seed lives in `params.yaml` — nothing
  is hardcoded in `src/`.
* Seeds are set for the split, the estimator initialisation and any sampling.
  Re-running the same commit reproduces `metrics.json` exactly.
* Preprocessing (when enabled) is fit on the **training split only**.
* The current Git commit SHA is recorded inside `metrics.json` under
  `provenance.commit_sha`, so a metric can always be traced to the code that
  produced it.
* The `.dvc` md5 of the raw dataset is recorded in `metrics.json` under
  `provenance.data_md5`.
* `pytest` runs without the dataset, so CI can test the code before anyone
  downloads 847 MB.

## Notebooks

Notebooks are stored as [jupytext](https://jupytext.readthedocs.io) *percent*
scripts (`.py`) so they diff and merge cleanly in review; the `.ipynb` twins are
generated on demand and stripped by the `nbstripout` pre-commit hook.

| Notebook | Covers |
| --- | --- |
| [`notebooks/01-eda.py`](notebooks/01-eda.py) | Archive inventory, class balance, label-integrity findings, near-duplicate capture frames, feature sanity check |
| [`notebooks/02-model-selection.py`](notebooks/02-model-selection.py) | Candidate comparison, speed/accuracy frontier, selection rule, reproducibility check |
